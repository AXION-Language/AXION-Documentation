值类型/引用类型的划分标准是什么？

性能？

int 小，所以直接拷贝影响不大差不多

object 可能很大，为了防止意外拷贝浪费内存，所以仅支持引用拷贝？

——但问题是object也可以很小；况且，你凭什么定义“意外”，万一我就是想拷贝一份object难道还不行了？


可变性？

int不可变，所以只能复制一份新的副本；object可变，所以可以在原对象上修改？

——说到底，凭什么123、“abc”就不可变了？凭什么{x:1,y:1}、[1,2,3]就可变了？数据大小并未变化（不会破坏既有的内存布局）凭什么不能变？


多线程安全？

因为要共享int、共享string，所以设计成不可变更安全？那难道array、struct、object...就不用共享了？

要多线程安全我自己不能去加锁？加同步？...

无论理由说得多么"煞有介事"，这始终只是语言设计者个人的武断选择

这个“特性”被做成了默认语义，而不是可选的显式行为

虽然，高级语言都有着与之匹配的GC机制，专门用来回收这些“不可达对象”

但GC也有运行时开销、也会存在延迟，对部分开发者而言，这可能是预期之外的


尤其在嵌入式开发、实时系统、游戏引擎的主循环、高频交易以及自动驾驶/工业控制这类对延迟或资源确定性要求极高的精密场景中，一次不可预知的 GC 停顿往往是致命的

根本问题：这不是我的选择，而是语言强加给我的

函数传参的二义性

function change(a) {

    a = 2;           // 改的是副本

    a.val = 2;       // 改的是原对象（如果a是对象）

}


let x = 1;           // 值类型

change(x);            // x 仍是 1，没变


let y = {val: 1};    // 引用类型

change(y);            // y.val 变成2

问题实质：函数参数的行为不由调用者控制，而由被传对象的类型决定。程序员必须记住每种类型的传参规则。

程序员失去了对“什么时候拷贝、什么时候共享”的控制权

语言替用户做了决定，而这个决定违背了人类的基本世界观

基本类型里，如int、string....是值类型，赋值就是数据拷贝✔

object、array...等是引用类型，赋值就仅拷贝指针，结果导致多个变量指向同一对象

-- 字符串String在内存上可能被js处理成指向同一块内存

但在用户接口层面，用户感受到的就是值拷贝，修改b不会影响a

-- 与String不同，这些引用类型可直接在用户接口层面感受到：

多个变量指向同一对象，修改其中一个就会影响其他

而这只是js的规则，实际上每个语言的分类规则都不同，开发者必须分别记忆

由于指针相关的问题过于复杂，用户编程压力大

以致于JavaScript、Java、Python.....等语言，则直接彻底舍弃指针（用户无法定义与操作指针）

转而去封装所谓的“数值对象”“引用对象”，但这又引入了新的问题.....

以JavaScript为例：

Go语言的数组是值类型：arr2 := arr1 是完整复制整个数组，改 arr2 不影响 arr1

例如

C系列的结构体struct(对标js的object)是值类型

JavaScript 和Java 的 String 在内存存储方式上是“引用类型”（像数组一样）——拷贝时是只拷贝地址

但修改时却表现为“像值类型”——修改b会创建新副本，不影响a

.....总之，不同语言的规则不尽相同，如果你需要同时用到多门语言，就需要被迫去记忆不同规则，转型成本很高

开发者过于依赖GC，而非语言逻辑本身，容易在不经意间导致内存泄漏

function f() {

    let inner = new Array(1000000);  // 内层大型对象

    outer = inner;   // 外层变量引用了内层对象

}


let outer;  

f();


// 函数结束后，inner 这个变量没了，但 outer 还指向Array(1000000)这段数据，导致其无法释放，产生内存泄漏

这不是GC误判（GC不会误判），问题在开发者自己身上，但

理论上，你当然可 手动 outer=null 来解除引用，确保Array(1000000)因un-reach-able而被GC回收

这确实可通过良好的编程习惯来避免，但没人可以确保自己的代码不出不出bug——更关键的这个bug的结果不是显式报错，而是在暗地里偷偷吃掉你的内存，难以察觉


编译器也无法对 outer=inner 给出任何提示或警告，这进一步加大了排查问题的难度

因为编译器并不知道inner本身是否直接持有Array(1000000)这个对象，例如

function f() {

    let inner = outer1; // Array(1000000)不一定是局部变量，可能来自于外部

    outer2 = inner;   // outer2通过inner间接持有newArray(1000000)的引用，这是合理的，所以编译器难以对"outer2 = inner"这句话本身给出风险提示

}


let outer1=new Array(1000000);  

let outer;  

f();

一切问题都只能靠开发者自己人工读代码来判断，大型项目里一旦出现内存泄漏，将会非常隐蔽，极其难以排查
