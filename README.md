————————————————————————————————————————————————————
 
C指针被信奉为不可动摇的底层真理   
js、python...告诉我区分值和引用是不可逾越的编程法则  
java让我把世界抽象为类与接口，并规定我只能一切从class开始  
rust让我做好不小心写个a就会失去所有权的心理准备    
...  

$\color{#008000}{\text{——我学得越多，越觉得自己在成长，可实际上只是在自我驯化并引以为傲}}$   


<br>

我必须把正常的世界观扭曲重构，再辅以各种设计模式、编程技巧、层层封装....最终强行塞进某个语言允许的框架里  
而细思极恐的是，一半以上的编程负担都源自于语言本身的设计缺陷  

$\color{#008000}{\text{——我失去的不止是效率，更是作为一名思想者的尊严}}$  
<br>

投奔高级语言？那就丧失了对底层硬件的掌控力；回归底层语言？那就得面对满屏的&和*  

$\color{#008000}{\text{——我试图选择，但也害怕失去，于是只能...}}$  

用Python列表推导做数据清洗，用C读写传感器缓冲区，用js写响应式站点，用java写高并发微服务，用Lua写游戏mod...

$\color{#008000}{\text{——这些成本从未被算进“技术债”，反而被美其名曰“技术栈”}}$

你所需的，将纤尘不染 ; 不想要的，则绝不存在 ;

# AXION不止用于编程，甚至初衷都与编程无关  

#### AXION一开始的目标人群，根本不是开发者，而是产品经理  
产品经理行业长期缺乏标准，需求文档的就是重灾区  
明明脑海里有完整的设计思路，但一到写文档就发现逻辑怎么都写不清楚  

<br>

#### 开发者有编程语言，但产品经理什么有什么？  
靠老掉牙的《系统分析与设计》专业课？靠 “用户画像、用例、字段、功能性/非功能性需求”...这种“过家家”式理论？
 $\color{#008000}{\text{——40\\%逻辑错误且有误导性，40\\%正确的废话，有价值的不超过20\\%}}$ 
 
 
靠各种鱼龙混杂的PM社区？   
 $\color{#008000}{\text{——乍一看专业到令人跪拜，细一品是根本无法作为方法论 的 模板与案例，全背下来也没用啊}}$  
 
 
靠自己多年经验潜心摸索总结一套自己的文档规范？  
$\color{#008000}{\text{——我不是没努力过，改了十多版方案都未获得满意的成果（总会遇到无法解释的新问题）}}$ 


还是靠那些烂大街的所谓产品经理培训课？  
$\color{#008000}{\text{—— 没亲自体验过从垃圾堆里爬上来，根本体会不到产品经理这行业有多臭: }}$   
$\color{#008000}{\text{格式规范却缺乏逻辑根基（画图工），头头是道却不产生实际价值（伪专家），吃着资历饭还以为自己不可替换}}$  

...  
<br>  

#### 无论心底是否愿意接受，但答案早已明确：  
$\color{#008000}{\text{产品经理这行业缺的根本不是业务知识 ：在行业里呆段时间，任何人都能掌握个大差不差，没有过多探讨的价值  }}$  

$\color{#008000}{\text{像程序员那样，一门【能承载任何设计思想的产品语言】才是真正匮乏的  }}$

# 本文档按 先Tutorial 后Documentation 进行组织
### Tutorial 教程
这个Turorial并不是上来就教你如何写代码  
而是从0开始，带着你分析与推理，不断重复“发现问题->分析原因->解决问题”这个过程  
<br>
如同一次次的 add 、commit、push  
你会清晰感受到对传统编程的逐步颠覆与重构、重新审视世界、并逐步升华自己的认知   
这是一个具有路径感、推理感、叙事感的过程
<br><br> 
### Documentation 文档
相当于整合了全部commit后的最终release   
是标准化、模块化、易于查阅的文档，是可用于编译与生产的最终解决方案  
<br><br> 
>短时间内仍以Tutorial为主进行更新  
>因为Tutorial包含全部逻辑，能解答你对编程语言的任何疑问  
>Documentation 只是合并归纳，逻辑上不是必需
