用  ::   或  => 当做【解释符】， 或自己随便编一个

一开始设计时，是用=>当解释符的，因为当时想着是和 指针-> 对应起来

AXION不约束表示层语法，自己怎么喜欢怎么来，只要逻辑正确就行

int a ：10

int b -> a

int c => a

-- 指针有#addr的内存成本 + 运行时动态转发的指令成本

-- 解释是编译期的静态转发，运行时0成本

但后来还是改成了  :: ，因为是想着和 实例型句柄：对应起来

int a ：10

int b :: 10

-- a是个初值为10的int变量，因此这个int对象需长期占用内存，长期维护

-- a就是10这个值！不占用固定内存，只在诸如 b+5 这种过程指令里被当做操作数

总之，AXION目前默认使用 双冒号 :: 当做【解释符】

【解释符】只是最底层的符号，上层可封装不同的应用场景

random(...){...}

随机数 => random(0..100)


count(...){...}

数量 => count(仓库货物)


姓名 ：李菊福

姓 => 姓名[1]

名 => 姓名[2..]


姓：李

名：菊福

姓名 => 姓+名

解释语句

move (t,pos,v){........}

move {target} to {position}  with  {vehicle}  =>  move (target,position,vehicle)


move A to 127,361 with A.car

回顾刚刚举的一些例子，它们都是【解释符】的运用

这是【解释型句柄】，拿来定义对象的

这是【指令模板】

当然，未来也会有其它基于【解释符】用法.....

为什么要这么刻意区分？

int   a   ： 10

int   b   ::   2a+5


“一招鲜”看似美好，但两种场景的编译规则是不同的，必须保全一个，“抛弃”另一个

解释型句柄：是按对象定义的标准来编译的

这个位置必须是Type

这个位置必须是 句柄名称

move {target} to {position}  with {vehicle}  ::  move (target,position,vehicle)


指令模板 ：则遵循另一套的标准

首项单词将作为行为标识

不得重复

中间用大括号 {....} 当做slot，可被替换为变量或表达式

其他诸如则被视为语句关键字，参与到模板签名中 move T to T with T

-- 使用时

-- 相当于move( A, (127,361) , A.car )

两套不同的编译规则，不可同时存在

如何解决？

方案一：用符号区分

解释型句柄用 ::

-- 最容易想到的办法

int   b   ::   2a+5

指令模板用 =>

move {target} to {position}  =>  move (target,position)

错是没错，但感觉差点味道，因为这样得再多占用一个符号位——编程语言里每个“符号位”都很宝贵，能节约尽量节约

方案二：保护唯一解释符::，用上下文区分

-- 这是AXION目前采用的方案

还记得之前我们从自然语言中获得的启发吗？

——每当你纠结 一词不可二用时，就可以尝试能否通过上下文来解决问题

int   b   ::   2a+5

解释型句柄用 ::

指令模板仍然用:: ，但要用类似def 、define....的关键字声明：这是一个关于指令模板的上下文

DEFINE  {T a} + {T b}  ::  2a+2b

-- 有了DEFINE 关键字做上下文的区分，指令模板就可以在自己的范围内随意定义规则，连首项的【行为标识】都可以省去

-- 关键是节约了=>这个符号，未来可以做其他用途（例如传统编程里的什么 强引用 弱引用 ....之类的）

 :: 这个符号在AHK里也是有类似“解释”的含义

F5 :: Reload

F4 :: Suspend Toggle

LButton ::

    send,{LButton}

    Sleep, 300

    send,{WheelUp}

Return

-- 我个人经常用AHK，所以 :: 在我心中的权重更高一些

用类似DEFINE关键字前缀标识上下文只是最简单的情况，但你需要注重的是其方法论本身

实际上还有很多功能并没有这么直白的前缀，但依然需要你能想到通过上下文来解决

例如之前“利用句柄上下文+类型上下文 解决 代理递归的问题”就是其一，之后还有其他需要通过“隐式”上下文解决的问题
