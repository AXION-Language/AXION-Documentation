回顾刚刚举的一些例子，它们都是【解释符】的运用

这俩都是【解释型句柄】的范畴

当然，未来还会有其它基于【解释符】用法.....

为什么要这么刻意区分？

int   a   ： 10

int   b   ::   2a+5


两种场景的编译规则是不同的，必须保全一个，“抛弃”另一个

解释型句柄

这个位置必须是Type

这个位置必须是 句柄名称

move {target} to {position}  with {vehicle}  ::  move (target,position,vehicle)


模板指令：遵循另一套的标准

首项单词将作为行为标识

不得重复

中间用大括号 {....} 当做slot，可被替换为变量或表达式

其他诸如则被视为语句关键字，参与到模板签名中 move T to T with T

-- 使用时

-- 相当于move( A, (127,361) , A.car )

两套不同的编译规则，不可同时存在

如何解决？

方案一：用符号区分

解释型句柄用 ::

-- 最容易想到的办法

int   b   ::   2a+5

模板指令用 =>

move {target} to {position}  =>  move (target,position)

错是没错，但感觉差点味道，因为这样得再多占用一个符号位——编程语言里每个“符号位”都很宝贵，能节约尽量节约

方案二：保护唯一解释符::，用上下文区分

-- 这是AXION目前采用的方案

还记得之前我们从自然语言中获得的启发吗？

——每当你纠结 一词不可二用时，就可以尝试能否通过上下文来解决问题

int   b   ::   2a+5

解释型句柄用 ::

指令模板仍然用:: ，但要用类似def 、define....的关键字声明：这是一个关于指令模板的上下文

DEFINE  {T a} + {T b}  ::  2a+2b

-- 有了DEFINE 关键字做上下文的区分，模板指令就可以随意定义规则，连首项的【行为标识】都可以省去

-- 关键是节约了=>这个符号，未来可以做其他用途

用类似DEFINE关键字前缀标识上下文只是最简单的情况，但你需要关注的是方法论本身


实际上还有很多功能并没有这么直白的前缀，但依然需要你能想到通过上下文来解决

例如之前“利用句柄上下文+类型上下文 解决 代理递归的问题”就是其一

之后还有其他需要通过“隐式上下文”解决的问题，例如在AXION里条件上下文内， = 直接用于值比较，而不需要写 == （无需手动与=赋值区分）.....

--实际是需要写TYPE的，这里只是快速说明问题
