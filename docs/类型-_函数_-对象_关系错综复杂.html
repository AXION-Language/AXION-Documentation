1、我们常说的Function、Object、Array....你以为它是一个“类型”，但实际上它们是同名的函数，作为构造方法

let a = new T() 实际上就是在调用一个名为T的函数

-- 然而大部分时候它们没有明确的生产价值，反倒成就了各种 收费课程 和 面试题

2、每个函数都一定具有.prototype属性，目的是让刚刚那个实例  a.__proto__ 指向 T.prototype （js里的指向是用=表示）

浅析JS类型系统

3、这样设计的效果是——

定义T类型时

-定义构造方法function T (){...}

-定义T.prototype={..T实例公共属性...}


使用时

-通过a=new T()产生了实例，自动修改a.__proto__=T.prototype

-该实例通过 a.x 又刚好能够调用T类型的公共属性(定义在T.prototype里)

这样就快速搭建起了一个【类型系统】

Function本身是名为Function的函数，所以Function.__proto__ 得指向 【函数的prototype：所有函数的公共属性】

但问题是JS里根本没有真正的【函数的prototype】，只有同名的【Function.prototype】——真正的函数是function Function(){...}里小写的这个function

所以最终就变成了【Function.__proto__】指向了【Function.prototype】


疑问：

其他T类型的实例【a.__proto__】都是 【T.prototype】，那理论上函数实例 【function a.__proto__】 也应该指向【function.prototype】,而不是指向【Function.prototype】

结果JS里并没有【function.prototype】，只能搞个同名的【Function.prorotype】假装一下？

这涉及 instanceof 的判断逻辑：

A instanceof B 实际上检查的是 B.prototype 是否在 A 的原型链上

对于那些自定义T类型，new T() instanceof T而言没问题

但对于最底层循环引用的Function和Object，就开始混乱不清了

真正违背常理的其实是——

A instanceof B的语义是“A是B的实例”，则理论上 A应该是实例，而B是类型

但实际上，JS里类型的本质是同名函数

这就导致了 Function、Object、Array....这些本该是处于“类型插槽(位置B)”的概念，被放到了“实例插槽上(位置A)”而导致语义混乱

我们没必要过分指责“B.prototype 是否在 A 的原型链”这个设计，这姑且可以理解为JS自己的策略，是一种选择

对于从其他语言转到JS的开发者而言，这无疑是最头痛的问题，因为总会免不了把其他OOP语言的“继承”和JS的“原型链”混为一谈

——从属性访问层面，两个概念结果一模一样，所以很像；但从语义 和 底层实现层面，则完全不同

问题的根源——JS的【类型】 是基于【函数】 来实现的

每个 T 在作为【类型】存在时，又同时以 【函数实例】的概念存在

其他OOP语言里，子类继承父类，是严格的单向关系———这很容易理解

而到了JS里，我们会看到 Function 继承Object; 与此同时，Object 又继承 Function

本来很简单的问题，却变成了类似于“波粒二象性”这样一个的哲学色彩的烧脑问题
