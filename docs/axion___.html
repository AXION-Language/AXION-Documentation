用int只是方便举例，任何类型在AXION都是这套规则，和传统编程类似Integer之类的"伪包装"完全不同

new Integer(1) + 1 // 自动拆箱为int再做加法

AXION解包是0成本的

之所以能够实现，是建立在【Property#Handle :: Object=Payload + @Property】 这套模型基础上的

单看结果是不是很容易理解？ ——  这正是AXION与人类认知高度融合的证明

但实际上这事并不简单，迄今为止学习的任何一个要素都必不可少 —— 任何一条细微的有差错，上述运算过程都只能是“空头理想”或导致“严重错误”

传统编程没有这套完整的逻辑通路，所以注定要拐弯抹角

没有句柄，就没有句柄属性

没有句柄属性，就只能凡事从定义class开始

没有Object-Property，“属性和成员就必须死一个”

没有Object=Payload + Property ，就只能用.value/运算符重载

....

上面还没举指针的例子呢，不然更加眼花缭乱... （而一路学过来你也应该清楚：AXION里，指针对上述逻辑没任何影响，因为AXION指针实现原理不同，而且还区分了句柄操作/对象操作 )

其他诸如：对象/非对象、对象/值、属性、引用/非引用、可变/不可变.......之类乱七八糟的错误思想，但凡沾点边，那就彻底不沾边了...

但“拆箱”这一步是有成本的：

Java 编译器会在字节码里插入一个 intValue() 方法调用，把 Integer 对象里的那个 int value提取出来，然后才能做加法

而在AXION里"解包"是0成本

new AngleInt(1) + 1  -- 解包为int payload + 1 

意思是在编译时就已经被变成 int payload + 1 了，运行时0成本

上文只举了一层包装的例子，但实际上，无论多少层包装，也和 int + int 性能完全一致

-- 看到这个intValue 和value 你就应该懂了，传统编程所谓的“包装”只是文字游戏

1、本质只是一堆平级成员堆在一起，根本没有Payload-Property这个架构

2、Integer是java写死的，开发者自己无法自己去写一个包装类并指望java给你自动"拆箱"
