句柄是【统一资源访问入口】

int a = 10

int b -> a

无论是静态/动态，也无论编译型/解释型，在AXION的世界观里，句柄只是抽象的【统一资源访问入口】，而绝不实际占用内存！

不是b

而是“b的符号表"

句柄类型：指针型

对象类型：地址

解引用类型：int

句柄类型：实例型

运行时 内存

b

3个句柄，但实际只占2份内存——占内存的一定是对象，句柄一定不占内存

a和b两个句柄都代表10这个数据，所以可以说：对象a和对象b的值是10 

句柄b_ADDR代表0x1000这个数据，所以可以说：对象b_addr的值是0x1000


【方法论】


第一步：明确最终目的，解释清楚 "你到底想用这个符号，代表什么对象"

例如在AXION的指针里，这个符号代表的是最终目标对象，而非指针本身(内存地址)


第二步：将其他所有的一切相关概念，都定义成【属性】来避免语义冲突

例如上面这个0x1000地址不是b，而是【b的地址】

符号表里的“b”，也不是b，而是【b的符号名】


甚至连【对象】也是【句柄的属性之一】

【对象b】的完整逻辑是【b所代表的对象】——句柄b.代表的对象

在指针问题里，b可能会在运行时改变指向——b从未改变，但b所代表的对象变了

--AXION本质是编程范式 与 世界观，所以本身并不限制你必须用 静态/动态、解释型/编译型

--只是目前个人精力有限，所以目前默认是按 “静态+编译型” 进行处理的——因为这是最底层的逻辑架构

--任何 “动态+解释型” 基于“静态+编译型”实现的

例如你可能会问“像js之类的解释型语言，不是有保存符号名吗”，凭什么能说“一定不占内存”？

不是a，而是"a的符号名/变量名"

看似是废话，而实际上正是传统编程几十年未解决指针问题的根源

通过本节的世界观与方法论，你可以跨维度精准定位任何资源，而不会出现歧义，这也是一切其他理论的基础

无论是运行时、编译时，符号的语义没有出现不会冲突——a只代表你所指定的那个对象，其他所有相关资源都是 a的xxx

类比现实——

产品：台灯

其他：产品制造、产品仓储、产品销售.....都是“产品的属性”

无论什么维度下，产品的语义都是固定的

所谓“跨维度”
