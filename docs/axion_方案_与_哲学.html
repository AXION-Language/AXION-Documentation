-- 思考：上述推导过程，对我们现在的问题“如何对 解释值 这种情况进行签名”有何启发或帮助呢？

a : T 真正的应用场景是 【解释值】

int a : 10

int b :: a

-- T 写左边，表示【对象】

左边的 int b 代表：

b是个对象，与a共享10这份数据 —— b被解释为a对象

既然b是对象，所以一定有伴随Type —— 之前章节推导过 "Object 与 Type 强绑定"

左边的int 正是 b 之所以作为一个对象的标志

T b :: 只允许【对象】

int a : 10

int b :: 20

所以之前我们举例的写法是错误的！

-- ❌️ int b 必须解释为对象，不可接受值

b :: T 则用来代表【值】

a :: int 10


b ::int  20


b :: int a

-- 直接写字面量20时，“最好”也写明 int —— 光写20无法确定是不是float类型

 -- 写变量名时，必须显式标记 T 类型 —— 这不是为了编译，而是为了开发者自己：根据b的定义就直观知道是个值，不用再往前翻代码了

仔细想一想为什么？如何理解？世界观上有何不同？

b :: int 20

b是对象吗？——显然不是，b没有独立内存； b只存在于指令中

既然不是对象，那b本身不需要  T b 这种约束

b :: int 20 啥意思？

在我眼里，b就是就是20 —— 任何时候我看这个b，它都应该是 20

任何时候，20这个值客观上一定是int类型 ——  b无权否定20就是int这个客观事实

int a : 10

int b :: a

b = b + 5

这是巧合吗？还是Quick Fix？

不，这是AXION基于人类认知进行建模的必然结果，是逻辑的天然终点

只要你的世界观不崩塌，任何逻辑在AXION里总会刚好处在它该在的地方，严丝合缝

最后，介绍下编译实现

符号：a

对象类型: int

句柄类型：实例型

offset：0

在传统编程里，你需要去理解为“20到底算值还是算对象”

Integer / int 到底是世界观层面的必然，还是某家语言的一己之见

关键是对象类型的Integer成本比int高了一大截，各种元数据、指针、引用.....塞入，已经远远超出理念层次的问题了


而在AXION里，我们并未引入任何新类型、新概念，而仅仅是利用现有框架巧妙解决

数字 20 任何时候都是 int 类型，在这一点上不存在任何心智负担

区别只在于到底是int对象还是int的值，对象有内存有地址可改；值只存在于指令里，没有独立内存与地址
