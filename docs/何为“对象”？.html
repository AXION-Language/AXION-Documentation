Property

Object 不是【客观存在】，而是人类主观认知层面的【关系模型】，体现在两方面：

Object = Payload + Property

这句话对我们的当前工作的指导意义是：

单纯用来指代一个【客观存在】已经有太多类似的概念了，例如：东西、实体、事物、个体、数据、物体、实例.......

所以，我们一定不要让【Object】去蹚这个浑水

而是应该跳出【客观存在】这个框架，赋予Object全新的定义

既然都说 Object 有 Property，那就针对这一点进行建模

Object 包含 Payload +Property，是向内查找

而不是Object之外，再额外拥有Property——这就变成向外查找了，是错误的

一、Object 与 Type 强绑定

用于描述客观存在的“东西、事物、物体...”这些概念可以没有Type，无所谓

任何一个Object，都一定有Type —— Type可以为Null，但架构层面必须得有

所以理论上，当我说Object的时候，逻辑上都应当包含 “T类型的Object”这个语义

当然也可以进行省略

-- 未给int维护任何对象属性，但丝毫不妨碍AXION里的int是个对象

1、句柄属性依旧随便加

2、一切行为都遵循统一的对象操作准则，和任何其他对象都一样

最关键的是，在AXION里“int是Object”是0成本的——

1、int永远只占4字节内存，不会像传统编程那样搞出个复杂的包装类，再塞入一大堆额外数据

2、也不会像传统编程那样，需要经过运行时装箱构造出一个Integer实例，还有指针跳转的开销

3、更不会因为架构上Object = Payload + Property，而给Property始终预留一个内存槽位

说到底就4字节的数据，哪那么多事....

一切额外成本都源自于传统OOP理论的不科学导致的（这种跟 编译型/解释型，动态/静态 这种具体策略无关，而是纯粹的设计缺陷）


AXION的世界观是透明的、简单的、直接对应物理事实的

没有属性就不占内存，没有隐藏要素、隐藏机制偷吃成本

（注意，现在我们在建模，而不是在回答问题）

-- 其实AXION里完全支持给class int 添加属性，并允许你用 a@xxx 访问

只是不能加在个体属性上：因为基础类型的【实例】必须是纯粹的(没有额外结构的)，不然就死循环了；

而是加在公共属性中：class int 里的公共属性里的 数据、方法随便加，都可以用  a@xxx访问
