共同点——理解

在长时间的生活过程中，人们不断在“学习”这些说法或概念，最终能够“理解”，知道其背后真正的语义

但在开发场景中，我显然不需要编译器擅自去学习或理解什么

而是希望约定一种方式，直接向编译器“解释某个概念的语义”，编译器直接照做即可

random(...){...}

随机数 => random(0..100)


count(...){...}

数量 => count(仓库货物)


姓名 ：李菊福

姓 => 姓名[1]

名 => 姓名[2..]


姓：李

名：菊福

姓名 => 姓+名

可以解释数据

假设用 => 当做【解释符】

也可以解释语句

drive(...){...}

drive {车} to {地点} = > drive( 车 , 地点 ）


move (t,pos,v){........}

move {target} to {position}  with  {vehicle} =>move (target,position,vehicle)


move A to 127,361 with A.car

那么就让我们更极端一点

int a : 10

memWrite (10, 0x1000)

int a => int (0x1000~)

是的，它等价于：

-- 先写数据，假设把a写到0x1000（偏移或地址都是编译器自由规划的）

-- 再告诉编译器 a 的就是 0x1000地址所存放的数据

即，从技术上说，AXION底层只需【解释型句柄】即可定义一切

 【实例型句柄：】【指针型句柄->】都不是必需的 —— 它们都是上层语法糖

这种用【已知概念】 解释 【新概念】的方式

是不是很像自然语言呢？

-- 或者反过来

解释——是语言的底层逻辑

任何一门语言，本质上都是在向编译器解释某个语法的含义 —— AXION所做的，只是允许你亲手触碰它

【实例型句柄】这种几乎可以算是最最底层的语义，是不是也可以被解释呢？

所以说，本质上a这个符号只是给开发者看的助记符，编译器底层是把它转成 内存地址 或 偏移量的

-- 一般除了裸机嵌入式是编译器写死地址，对于大部分应用，编译器只提供偏移，由链接器分配地址

-- 使用时

-- 相当于move( A, (127,361) , A.car )

AXION【解释符】是基于语义的，所以不存在【预编译宏】里的各种问题

类型系统

AXION：本质是定义一个人类认知中的概念级对象

只要是对象，就依旧遵守类型规则

int sub5(int x) =>  x - 5


main() {

    int money = 100

    int result = sub5 (money)

    print result

   


    string moneyStr = "100"

    int result2 = sub5 (moneyStr);

    print result2

}

-- 95 ✔️

-- 误传字符串时，编译器应该报错提醒我

-- Type Error：需要int但传入string ✔️

-- 不会被执行 ✔️

#define SUB5(x) x - 5


int main() {

    int money = 100;

    int result = SUB(money);

    printf("%d\n", result); 

   

    // 误传字符串时：

    char* money_str = "100";

}

传统【预编译宏】无视类型系统和其他一切语言规则，容易埋下安全隐患且难以调试

-- 整个SUB5返回值没有类型，参数x也没有类型

解释逻辑不会在预编译阶段就当做纯文本被处理掉，它会像其他正常语句一样正常提交给编译器，受语法规则控制
